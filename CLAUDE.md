# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SPIRE is the SPIFFE Runtime Environment: a server + agent toolchain that attests workloads and issues SPIFFE IDs / SVIDs (X.509 and JWT). It is a CNCF graduated project. This is `github.com/spiffe/spire` (here, an Indeed fork). This branch, **`too_many_jwks_keys_2`, is cut from `upstream/main`** (not the Indeed `main-indeed`) and reimplements the "too many JWKS keys" fix using a datastore-coordinated single JWT-key authority (see "The task" below). The earlier `too_many_jwks_keys` branch took a different approach (per-KeyManager-plugin locks); the section "Why this branch is better" explains the change.

## Build / test / lint

Everything goes through the `Makefile`, which pins and auto-installs its own toolchain (protoc, golangci-lint, Go) under `.build/`. Use the make targets rather than raw tools — notably, `make lint-code` runs golangci-lint via `go run .../golangci-lint@<pinned-version>`, so a system-installed `golangci-lint` of a different version (which fails against this repo's Go target) is irrelevant.

- `make build` — build all binaries (`bin/spire-server`, `bin/spire-agent`, `bin/oidc-discovery-provider`); `make bin/spire-server` for one.
- `make test` — full unit suite (`go test ./...`). `make race-test` for the `-race` variant. `COVERPROFILE=out.cov make test` for coverage.
- `make lint` — `lint-code` (golangci-lint, config in `.golangci.yml`) + `lint-md`.
- `make all` — build + lint + test.
- `make generate` — regenerate protobuf / plugin / service `.pb.go` from `.proto`; `make generate-check` verifies generated code is current (must run on a clean tree). Run after editing any `.proto`.
- `make govulncheck`, `make tidy` / `tidy-check`.

Running focused tests directly with `go test` is fine and faster than `make test`:

- Single package: `go test ./pkg/server/ca/manager/`
- Single test: `go test ./pkg/common/bundleutil/ -run TestDedupSigningKeysByKid`
- Datastore and several plugins use **testify suites**, so the top-level `Test*` is the suite entry and methods are addressed with `/`: e.g. `go test ./pkg/server/datastore/sqlstore/ -run 'TestPlugin/TestBundleCRUD'`.

Datastore unit tests run against **sqlite3** by default. MySQL/Postgres dialects are exercised via the integration harness (`test/integration/`, `make integration`), not plain `go test`.

## Architecture

Two processes, mirrored layouts: `pkg/server/` (the trust-domain authority) and `pkg/agent/` (runs on each node, attests workloads, exposes the SPIFFE Workload API). CLI entrypoints are in `cmd/spire-server` and `cmd/spire-agent`; `support/oidc-discovery-provider` serves a JWKS/OIDC endpoint from the trust bundle.

**Plugin framework (central).** Almost all pluggable behavior is a gRPC plugin built on `github.com/spiffe/spire-plugin-sdk`. Plugin categories live under `pkg/{server,agent}/plugin/<category>/<impl>/` — server: `keymanager`, `nodeattestor`, `upstreamauthority`, `notifier`, `bundlepublisher`, `credentialcomposer`; agent: `keymanager`, `nodeattestor`, `workloadattestor`, `svidstore`. Each impl exposes a `BuiltIn()` (`catalog.MakeBuiltIn(...)`); built-ins are wired into the process by being listed in `pkg/{server,agent}/catalog/<category>.go`. Plugins can also run as external binaries over the same gRPC contract, so an implementation must never assume in-process calls. The category interface package (e.g. `pkg/server/plugin/keymanager`) is the neutral contract shared by the host (CA manager, etc.) and the impls — put cross-cutting constants there, not in an impl or in `pkg/server/ca`.

**Server CA + HA rotation.** `pkg/server/ca/manager` prepares/activates/rotates the X509 CA, JWT, and WIT signing keys; `journal.go` persists rotation state to the datastore's `CAJournal` record. Multiple servers in one trust domain share the datastore (HA): each server finds *its* journal by matching a KeyManager key's X.509 SubjectKeyID against `active_x509_authority_id`. The rotator (`pkg/server/ca/rotator`) drives `Prepare/Activate/Rotate` for each key type on a 10s tick. Key material is obtained from the configured `keymanager` plugin by a deterministic logical key ID (`x509-CA-*`, `JWT-Signer-*`, `WIT-Signer-*`, built in `slot.go`); the bundle (`common.Bundle`) is keyed by the JWT `kid`.

**Datastore.** The `datastore` plugin interface (`pkg/server/datastore`) is implemented by `sqlstore` (GORM over sqlite/MySQL/Postgres). Schema lives in `models.go`; migrations are versioned (`migration.go` + dump-based migration tests in `sqlstore_test.go` `TestMigration`). Per repo convention, **a datastore/schema change must ship a full minor release before any code depends on it** — add the column/migration first, wire up the dependent logic in a later release. `withReadModifyWriteTx` provides a portable read-modify-write transaction (`SELECT … FOR UPDATE` on MySQL/Postgres) used for compare-and-swap style updates.

**Protobuf.** `.proto` under `proto/spire/` (public API/common types) and `proto/private/` (internal, e.g. the CA journal). Generated `*.pb.go` is checked in and produced by `make generate`; never hand-edit generated files.

## The task: shared JWT signing keys via a datastore JWT-authority lease (fix "too many JWKS keys", #4699)

In HA / nested SPIRE, every server independently prepares/activates/rotates its own JWT signing key, so the trust bundle's `JwtSigningKeys` (served as JWKS) grows ~`2 × server count`. JWKS consumers cap key counts (AWS OIDC ~100), which breaks federation at scale. Goal: the trust domain runs **one** shared JWT signing key that appears **once** in the JWKS regardless of server count, without breaking X509 CA issuance or the HA journal. Only **JWT** keys are shared; X509 CA and WIT keys stay per-server.

The approach (call it "Alt 2"): keep the shared key (AWS KMS forbids private-key export, so "sharing" means sharing *signing access*, not bytes), but elect a **single JWT-key writer** coordinated through the **datastore every HA server already shares** — not through per-plugin locks. One writer prepares/activates/rotates the shared key; every other server binds that key for local signing. Taint stays any-server: the lease carries the retired (OLD) authority so every server can satisfy the `localauthority` taint precondition. (This was a regression in the initial Alt 2 cut — the lease dropped OLD authorities — found via a verification test and now fixed; see the taint paragraph under "Why this branch is better".)

### Mechanics

1. **Deterministic `kid` + dedup (so one shared key = one JWKS entry).** `deterministicKeyID(signer)` (`pkg/server/ca/manager/manager.go`) derives the `kid` from the public key's SubjectKeyID (`x509util.GetSubjectKeyID` + `SubjectKeyIDToString`), used by `newJWTKey`/`newWITKey` (the old random `newKeyID`/`keyIDFromBytes` were removed). `bundleutil.DedupSigningKeysByKid` (`pkg/common/bundleutil/bundle.go`) collapses JWT/WIT entries sharing a `kid` (keeping max `NotAfter`, OR-ing `TaintedKey`); wired right after `MergeBundles` in `sqlstore.go` `appendBundle`. No-op when `kid`s differ — non-shared deployments unaffected. **Do not** change `MergeBundles`. Deterministic `kid` is *still required* even with a single writer: at failover the new writer must compute the same `kid` for the same key, or the bundle gains a duplicate.

2. **The JWT-authority lease (datastore single-writer coordination).** New `jwt_signing_authorities` table (one row per trust domain), schema **v26** (`migration.go` `migrateToV26`, plus the `TestMigration` v25→v26 dump in `migration_v26_test.go`). Interface on `datastore.DataStore` (`pkg/server/datastore/datastore.go`), implemented in `pkg/server/datastore/sqlstore/jwt_signing_authority.go` via `withReadModifyWriteTx`:
   - `AcquireJWTSigningAuthority(td, candidateServerID, now, ttl) → (lease, acquired)` — CAS: grant if absent / expired / already held by candidate; bump a **fencing token** on takeover; otherwise return the current lease with `acquired=false` (so a non-holder learns the active key). Retries a transient first-acquire deadlock (`dialect.isDeadlock`, bounded by `maxJWTSigningAuthorityAcquireRetries`) — see the cold-start gotcha.
   - `SaveJWTSigningAuthority(lease)` — persists the shared JWT slot state + active `kid`; rejected (FailedPrecondition) if holder/fencing no longer match (the caller lost the lease).
   - `FetchJWTSigningAuthority(td)`.
   The lease's `Data` is a serialized `journal.Entries` (reusing the existing journal proto — **no proto change**) holding the current+next shared JWT slots.

3. **Writer / follower coordination (`pkg/server/ca/manager/jwt_authority.go`).** The rotator calls `SyncJWTKeyAuthority(ctx)` at the top of `rotateJWTKey` every tick (no-op unless sharing is on). Sync acquires/renews the lease (TTL `jwtAuthorityLeaseTTL = 2m`, renewed each 10s tick) and **reconciles** in-memory JWT slots from the lease (`reconcileSharedJWTSlots` reuses `SlotLoader.getJWTKeysSlots` to bind shared keys via `GetKey` and `SetJWTKey` the active one — for both writer and follower). `PrepareJWTKey`/`ActivateJWTKey`/`RotateJWTKey` are gated: a **non-writer returns immediately** (it already bound the shared key in Sync); the **writer** runs the normal lifecycle and then `persistJWTAuthorityState` writes the slots back to the lease. On **failover**, a follower whose Sync now acquires the (expired) lease adopts the existing shared key from the lease `Data` (no duplicate mint) and resumes rotation.

4. **Config.** Server-level `jwt_key_sharing` (HCL `cmd/spire-server/cli/run/run.go` → `pkg/server/config.go` → `manager.Config.JWTKeySharing` in `pkg/server/server.go`). When enabled, the manager generates a per-process `serverID` (UUID) used as the lease holder identity. A restart is therefore treated as a failover (re-acquire after lease expiry).

5. **JWT-vs-other key distinction.** `keymanager.IsSharedKeyID(id)` (true iff prefix `JWT-Signer-`); prefixes `X509CAKeyIDPrefix`/`JWTSignerKeyIDPrefix`/`WITSignerKeyIDPrefix` are exported from `pkg/server/plugin/keymanager/constant.go` and used by `slot.go` (and, once Task 4 lands, every plugin). X509 CA / WIT remain per-server, so `findCAJournal`'s X509-SubjectKeyID binding is untouched and a server identifier is still required.

### Per-plugin mechanics (`pkg/server/plugin/keymanager/<impl>/`)

All four enable sharing via a per-plugin `shared_jwt_keys = true` config (must match the server's `jwt_key_sharing`). JWT keys (`IsSharedKeyID`) get a **shared, deterministic backend name** (no server identifier) so every server resolves the same key; X509/WIT keep their per-server names. Each plugin caches keys in memory, so a follower discovers the writer's newly-created shared key via **lazy fetch on `GetPublicKey` cache-miss** (the manager's reconcile calls this every 10s). The per-plugin distributed-lock/freshness machinery from `too_many_jwks_keys` is **not** present — the datastore lease handles write-coordination.

- **disk** (`disk.go`) — two-file model: `keys_path` holds this server's private X509/WIT keys; a new `shared_keys_path` holds the shared JWT keys (single writer). `writeEntries` splits by `IsSharedKeyID` and only persists the shared file when this process generated a shared key (no follower clobber); `GetPublicKey(s)` reload the shared file for freshness.
- **awskms** (`awskms.go`, `fetcher.go`) — shared alias prefix `alias/SPIRE_SERVER/<td>/shared/<keyID>`; composite `spireKeyIDFromAlias`; `fetchSharedKeyOnMiss` (DescribeKey/GetPublicKey by shared alias). **`disposeAliases` skips the shared prefix** so no server GCs the shared key.
- **azurekeyvault** (`azure_key_vault.go`, `fetcher.go`) — deterministic shared name `spire-key-shared-<keyID>` (vs per-server random-UUID names); shared keys tagged with trust domain only; `keyBelongsToServer`/`spireKeyIDFromKeyName` handle shared names; `disposeKeys` skips keys without a `spire-server-id` tag (shared keys) — also fixing a latent nil-deref.
- **gcpkms** (`gcpkms.go`, `fetcher.go`) — deterministic shared crypto-key name `spire-key-shared-<keyID>`; `fetchSharedKeyOnMiss` lists trust-domain keys and matches the shared name; **`disposeCryptoKeys` skips shared-named keys**. (The writer also discovers its own shared key via the normal per-server fetcher since the creating server's labels are applied.)

Tests: `TestSharedJWTKeys` (disk, awskms, azurekeyvault) and `TestSharedJWTKeyNaming`/`TestSharedJWTKeysGenerateNaming` (gcpkms). The gcp fake's `CreateCryptoKey` omits `/cryptoKeys/` from stored names, so gcp uses naming + generate-behavior tests rather than a cross-plugin lazy-fetch round-trip.

### Why this branch (Alt 2) is better than `too_many_jwks_keys`

The original `too_many_jwks_keys` solved the *count* problem by sharing one backend key and deduping by `kid`, but pushed cross-server coordination into each KeyManager plugin as hand-rolled distributed locks (KMS alias-as-mutex, GCS labels, Azure tags, file locks) with freshness windows and stale-lock breaking. Reviewer feedback (sorindumitru on PR #6537) flagged the unresolved hard part: *who* may rotate/taint/remove the shared key.

`too_many_jwks_keys_2` keeps the genuinely good parts (deterministic `kid`, `DedupSigningKeysByKid`, JWT-only scoping) and fixes the rest:

1. **Coordination at the right layer.** Mutual exclusion lives once, in the datastore every HA server already shares (`withReadModifyWriteTx` = portable `SELECT … FOR UPDATE` CAS) with fencing tokens — instead of being reimplemented, with backend-specific correctness arguments, across four plugins.
2. **Solves rotation authority, not just count.** A single elected *writer* owns prepare/activate/rotate; failover is explicit (lease expiry + fencing + state adoption from the lease). The old approach had no single writer: every server's manager ran the rotation lifecycle locally (ungated) and relied on per-plugin freshness windows — *without* fencing — to avoid double-minting the shared key, with correctness argued per backend. (Note the careful scoping to *rotation*: on *taint* authority specifically, that same "every server rotates locally" gave the old branch something Alt 2 had to earn back explicitly — now done — see the taint paragraph below.)
3. **Much simpler plugins.** Plugins only need shared JWT *naming* + discovery so `GetKey` resolves the shared key; all the lock/freshness/stale-lock code is gone (~the bulk of the old per-plugin diff).
4. **Robust rotation failover.** The lease records the shared JWT slot state, so a new writer *adopts* the existing key (no duplicate JWKS entry, no key churn) and resumes the schedule. (The `ds.TaintJWTKey` *write* is trust-domain-global by `kid` and lease-free; the manual-taint *precondition* is also met any-server now that the lease carries the retired authority — see the taint paragraph.)

**The one dimension where Alt 2 initially regressed — and the old branch was more elegant — is manual taint (now fixed).** `localauthority` *taint* can only target a server's `next` JWT slot when its status is `OLD` (`service.go:188-206`; *revoke* is looser — `validateAuthorityID` has a bundle fallback, so it was never affected). On the *old* branch taint worked on **any** server as an *emergent* property, with no retention code: rotation was ungated and local on every server, and `GenerateKey` reused the shared key within a freshness window, so every server's per-server journal independently converged to "old key = `OLD` in `next`." Alt 2 deliberately gave that up — it gates rotation to the writer and makes followers mirror the *lease* — and the initial cut persisted only the live (active+prepared) slots, dropping OLD authorities (`jwtKeySlotToEntry` skipped `jwtKey == nil`), so after a reconcile **no** server met the precondition (caught by `TestSharedJWTOldAuthorityRemainsTaintable`, then red; a manual taint succeeded only on the writer, only in the ~10s window before its next reconcile). The fix carries the retired OLD authority in the lease — `jwtKeySlotToEntry` reloads its public key from the KM (the signer was cleared by `Reset`) and `reconcileSharedJWTSlots` restores it into the `next` slot — bounded to the same rotation window as non-shared SPIRE (`…TaintWindow`). That re-earns taint-anywhere on a *more robust* substrate than the old branch: explicit, testable, fenced lease state vs. emergent retention that depends on freshness windows fragmenting `kid`s on desync. Honest verdict: Alt-2 now ≥ old branch here too, but the old branch got this for free (emergent) where Alt 2 had to implement it.

**The mirror image of taint — and a dimension firmly *for* Alt 2 — is cold-start.** When an HA cluster boots with no shared key yet, *who mints the first one?* The old branch has **no explicit cold-start handling**; safety is emergent and differs per backend: disk is safe (a blocking `flock` mutex), awskms is safe (its lock rides on atomic `CreateAlias`, and only the winner ever gets the shared alias — losers mint throwaway CMKs and schedule-delete them), gcpkms is safe at cold-start (deterministic CryptoKey *name* + GCP name-uniqueness) — but **azurekeyvault double-mints**: its lock tag is only checked when the key already exists (gated behind `GetKey…; if err == nil` in `azure_key_vault.go`), so at first boot the lock is skipped, every racer calls `CreateKey` (which makes a fresh *version* with new material), and the trust domain ends up with N distinct keys. Because the `kid` is **material-derived**, those are N distinct JWKS entries — **exactly the #4699 count bug the branch set out to fix** — and `DedupSigningKeysByKid` can't collapse them (different kids). There are **no fencing tokens** anywhere on the old branch, only wall-clock TTL/freshness. Alt 2 makes this **structurally impossible**: the unique `trust_domain` index guarantees at most one writer regardless of the race (one key → one kid; followers bind, never mint), and the only cold-start failure mode is a *retriable* MySQL gap-lock deadlock (handled by the lease-local retry — see the cold-start gotcha), never a correctness violation. So "emergent" cuts both ways: it gave the old branch taint-anywhere for free, and it silently reintroduces #4699 on Azure. (The Azure double-mint is a **static-analysis finding** — code-verified as structurally unpreventable at first boot, not yet runtime-proven.)

Trade-offs (honest): Alt 2 adds a datastore schema (subject to the minor-release rule, hence the migration/code split), introduces a single-writer lease (a bounded failover gap on writer death — `≤ jwtAuthorityLeaseTTL`; scheduled-rotation windows are days), and still requires the plugin shared-naming work above. A per-process server UUID means a server restart re-acquires after lease expiry rather than instantly. (Manual taint needed explicit OLD-authority retention in the lease — the old branch got that for free; see the taint paragraph.)

### Gotchas for the next agent

- **Deterministic-`kid` convergence is gradual.** On upgrade, existing keys keep their old random `kid` (loaded from the journal in `slot.go` `loadJWTKeySlotFromEntry`); only newly-prepared keys get deterministic ones. Start fresh when enabling shared mode.
- **FIPS** mode changes the SKI hash (`pkg/common/x509util/keyid.go`: SHA-256-first-20 vs SHA-1), so the `kid` differs by mode — servers sharing a key must run the same FIPS mode.
- **`loadJWTKeySlotFromEntry` uses real `time.Now()`** for the slot-expiry check (not the injected clock); relevant when writing clock-mocked tests around reconcile/failover.
- **Test fakes** return *deterministic* key material (`test/testkey`, distinct key per `GenerateKey` call) and `keymanagerbase.GenerateKey` overwrites an existing id — so `kid` equality is a valid proof that a follower *bound* the shared key rather than minting a new one.
- **Shared-key manual taint relies on the lease carrying the retired (OLD) authority** (`TestSharedJWTOldAuthorityRemainsTaintable`, `…TaintWindow`). After `RotateJWTKey` the rotated-out slot has `jwtKey == nil` (via `Reset()`), so `jwtKeySlotToEntry` reloads its public key from the KM (`GetKey(jwtKeyKmKeyID(slot.id))` — the backend key exists until pruned) and persists it; the entry's slot-load gate is satisfied because a just-rotated key's `NotAfter` is still in the future, and `loadJWTKeySlotFromEntry` then routes the `OLD` entry back into `nextJWTKey` so `localauthority` taint (`service.go:188-206`, needs `next` slot == target with status `OLD`) succeeds on every server. The persist guard is `authorityID == ""` (skip only *truly* empty slots), **not** `IsEmpty()` (which is true for OLD slots — using it was the original bug). Retention is bounded to the rotation window: once the writer prepares the next successor it reuses that slot, dropping the prior OLD authority from the lease. `RevokeJWTAuthority` was never affected (the `validateAuthorityID` bundle fallback). Contrast: the old branch retained OLD per-server *emergently* because every server ran `RotateJWTKey` locally.
- **MySQL cold-start gap-lock deadlock on first-acquire (handled by a lease-local retry).** When an HA cluster cold-starts, every server calls `AcquireJWTSigningAuthority` before the lease row exists; on MySQL the `SELECT … FOR UPDATE` takes an InnoDB gap lock (nothing to lock yet) and the racing `INSERT`s deadlock (error 1213), so InnoDB aborts all but one loser. Postgres does not (observed: 0 errors). Safety is never at risk — the unique `trust_domain` index guarantees exactly one writer — and it is **cold-start-only and self-healing**: once the row exists, every acquire takes the clean row-exists path (a real row lock, no gap lock), which `TestJWTSigningAuthorityConcurrentAcquire`'s takeover phase confirms. `AcquireJWTSigningAuthority` retries the deadlock (`dialect.isDeadlock`; bounded by `maxJWTSigningAuthorityAcquireRetries`); on retry the winner's row exists so losers get a clean `acquired=false`. Verified errored-losers=0 on real MySQL 8.0 / Postgres 13 under 16-way contention. The retry is deliberately **lease-local** — the shared `withReadModifyWriteTx` (15+ callers) was left unchanged. Detection rides on the raw error captured inside the op closure (the `gormToGRPCStatus` flattening at `withTx` loses the driver error, so the wrapped gRPC status can't be classified at the `Plugin` boundary).
- When adding a new exported symbol, no doc comment is required (`.golangci.yml` does not enable revive's `exported` rule). Run `make lint-code` (not a system `golangci-lint`).
